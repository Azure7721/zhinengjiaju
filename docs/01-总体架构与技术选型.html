01 · Architecture

总体架构与技术选型

目标不是“把 13 张图变成页面”，而是建立一套能持续加设备、加能力、加场景的系统。 本文档定义单仓结构、技术栈、模块边界、扩展机制、数据流与部署拓扑。

pnpm workspaces uni-app + Vue 3 NestJS + Prisma PostgreSQL + Redis + MQTT

1. 架构目标

可扩展

新增设备类型、能力、场景动作、协议，不复制页面、不改核心业务。

可验证

每条链路有测试：单元、集成、端到端、T0 虚拟、T1 BLE。

可运营

管理员能配置设备型号、查看日志、审计操作、模拟设备。

2. 单仓结构

smart-home/
  apps/
    miniapp/          # 微信小程序（uni-app + Vue 3）
    admin/            # PC 管理后台（Vue 3 + Element Plus）

    device-engine/    # 模拟设备引擎 + 虚拟 BLE 服务
  packages/
    shared/           # 类型、常量、错误码、工具
    contracts/        # OpenAPI、WS、MQTT 消息契约
  firmware/
    esp32-ble-sim/    # 可选：ESP32 BLE 外设固件
  infra/
    docker-compose.yml
    nginx/
  docs/               # 本计划文档集
  package.json
  pnpm-workspace.yaml
  tsconfig.base.json

使用 pnpm workspaces；不引入 Turborepo/Nx，减少学习成本；需要时再用 `pnpm -r` 并行执行。

6. 可扩展机制（核心）

6.1 设备模型元数据

设备型号不是代码里的 enum，而是数据库记录：

// device_model.metadata 示例
{
  "model": "ac.dual.v1",
  "name": "双模空调",
  "category": "climate",
  "capabilities": [
    { "key": "switch", "type": "boolean", "control": "switch" },
    { "key": "temperature", "type": "number", "min": 16, "max": 30, "unit": "℃", "control": "dial" },
    { "key": "mode", "type": "enum", "values": ["cool", "heat", "auto"], "control": "segmented" },
    { "key": "fanSpeed", "type": "enum", "values": ["low", "mid", "high"], "control": "segmented" }
  ],
  "commands": [
    { "name": "setPower", "params": { "value": "boolean" } },
    { "name": "setTemperature", "params": { "value": "number" } },
    { "name": "setMode", "params": { "value": "enum" } }
  ]
}

小程序读取 capabilities 渲染控制区；未知 control 走通用控件（开关/滑杆/输入），不会白屏。

6.3 协议适配器

interface DeviceAdapter {
  connect(device: DeviceRef): Promise<void>;
  disconnect(device: DeviceRef): Promise<void>;
  sendCommand(device: DeviceRef, cmd: DeviceCommand): Promise<CommandAck>;
  onTelemetry(handler: (msg: TelemetryMessage) => void): void;
}

实现：MockAdapter、VirtualBleAdapter、MqttAdapter、RealBleAdapter。业务层只依赖接口。

6.4 命令总线

REST 命令→ 校验/鉴权→ 幂等键→ 落库→ MQTT/BLE→ 设备 ack→ WS 推送

超时重试、失败状态、审计、重复 cmdId 去重；命令结果可追踪。

6.5 场景 DSL

interface Scene {
  id: string;
  name: string;
  triggers: Trigger[];   // manual / schedule / condition / deviceEvent
  conditions: Condition[];
  actions: SceneAction[];
  enabled: boolean;
}

触发器与动作都通过 strategy registry 扩展；新增“日落触发”或“延迟动作”只加策略，不改执行器。

6.6 动态 UI

小程序 ControlRenderer 根据 capability/control 选择组件；管理后台 SchemaForm 根据 JSON Schema 生成表单。设计稿里的四类设备只是模板，不是上限。

6.7 权限与审计

管理员 RBAC 到菜单/按钮；家庭角色 owner/admin/member；设备命令校验归属；所有写操作落 audit_log。

6.8 API 版本化

REST 统一 /api/v1；WS/MQTT 消息带 v 字段；破坏性变更升版本，旧版本保留一个迭代。

7. 三条数据流

遥测

设备引擎 → MQTT device/{id}/telemetry → server 订阅 → 落库 → WS 推送 → 小程序/后台。

命令

小程序 → REST → 校验/幂等 → MQTT device/{id}/command → 设备 → ack → server → WS。

场景

触发（手动/定时/条件）→ 执行器 → 逐动作命令 → 结果记录 → WS 推送执行进度。

8. 部署拓扑

开发/演示（单机）

server 3000、admin 5173、MQTT 1883/8888、虚拟 BLE 7001、PostgreSQL 5432；小程序开发者工具连 localhost。

Docker Compose 优先；不可用时本机服务；最后 SQLite + Aedes 兜底。

测试/生产（可选）

Nginx + HTTPS；server 多实例；PostgreSQL/Redis 托管；MQTT 用 Mosquitto/EMQX；对象存储放图片。

小程序 request/socket 域名白名单；体验版二维码。

9. 架构决策记录（ADR）

决策选择理由代价
小程序技术uni-app + Vue 3多端复用、团队熟悉、生态好部分 Web 能力不可用
服务端NestJS模块化/DI/守卫，适合长期扩展比 Fastify 裸写重
数据库PostgreSQL + JSONB关系 + 弹性元数据需要运维/迁移
设备信号MQTT + WS标准、可替换真实设备多一个 broker 组件
设备扩展元数据 + 能力注册表不写死按钮前期建模成本
BLE 测试ESP32 + 虚拟 BLE真实信号 + 无硬件可演示硬件/权限差异

10. 取舍与风险

  • 不要过度抽象：首批只做 4 类设备 + 1 个未知能力；等第二种设备型号接入时再补通用层。
  • 不要把权限放前端：所有归属与角色判断在服务端；前端只控制展示。
  • 不要用前端定时器代替信号：演示也走 MQTT/虚拟 BLE，保证链路真实。
  • 不要一开始上微服务：单 NestJS + 独立 device-engine 足够，按需拆分。
