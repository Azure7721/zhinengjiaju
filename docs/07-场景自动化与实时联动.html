场景自动化与实时联动

场景是“触发器 + 条件 + 动作序列”的规则，不是一段写死的 if/else。 执行器要能逐动作执行、记录状态、失败重试，并把进度实时推给前端。

Trigger / Condition / Action 状态机 BullMQ / Cron 逐项执行日志

1. 目标

  • 支持手动、定时、条件、设备事件四类触发。
  • 动作按顺序执行，支持延迟、重试、失败继续/终止策略。
  • 每次执行有 run + 逐 action 状态，前端实时可见。
  • 新增触发器/动作类型通过策略注册，不改执行器核心。
  • 避免循环触发、重复执行、并发冲突。

2. 场景 DSL

interface Scene {
  id: string;
  homeId: string;
  name: string;
  enabled: boolean;
  triggers: Trigger[];
  conditions: Condition[];
  actions: SceneAction[];
  policy: {
    onActionError: 'continue' | 'abort';
    maxRetries: number;
    cooldownSec: number;
  };
}

type Trigger =
  | { type: 'manual' }
  | { type: 'schedule'; cron: string; timezone: string }
  | { type: 'condition'; expression: ConditionExpression }
  | { type: 'deviceEvent'; deviceId: string; event: string };

interface SceneAction {
  id: string;
  deviceId: string;
  command: string;
  params: Record<string, unknown>;
  delayMs?: number;
}

3. 四类触发器

类型示例实现注意
manual点“执行场景”REST → 执行器幂等键/冷却时间
schedule每天 20:00 观影BullMQ repeat / cron时区、夏令时、错过的任务
condition光线 <30lux 且有人遥测/事件流评估防抖、持续时间、避免抖动
deviceEvent门锁打开 → 开灯事件总线订阅循环触发、事件风暴

4. 条件表达式

{
  "all": [
    { "deviceId": "d_light", "metric": "illuminance", "op": "<", "value": 30 },
    { "deviceId": "d_presence", "metric": "presence", "op": "=", "value": true }
  ]
}

支持 all/any/not；条件评估在服务端，基于最新设备影子/遥测；可加“持续 N 秒”避免瞬时抖动。

5. 执行状态机

queued → running → success
                ↘ partial
                ↘ failed
        ↘ cancelled / timeout
状态含义前端
queued已创建，等待执行排队中
running正在逐动作执行进度/当前动作
success全部动作成功完成
partial部分成功（按策略继续）成功 N / 失败 M
failed关键动作失败/策略中止失败原因 + 重试
cancelled用户取消/新执行抢占已取消

6. 执行器

  1. 创建 run：幂等键、触发来源、操作者；检查冷却/并发。
  2. 评估条件：不满足则记录 skipped，不执行。
  3. 逐动作：发命令 → 等 ack → 更新 action 状态 → 延迟下一个。
  4. 失败策略：continue 记录失败继续；abort 停止并标记 failed。
  5. 汇总：success/partial/failed；写 run 日志；WS 推送。
  6. 通知：可选给家庭成员发消息。

7. 三个示例

观影模式

投影仪开、灯关、扫地机关、窗帘关；执行按钮固定在执行区；逐项状态。

清洁模式

蒸烤箱/洗碗机/净饮联动；进度/剩余时间；水位不足 5% 停止并提醒。

回家模式

门锁事件触发 → 玄关灯开 → 空调 26℃ → 窗帘开 50%；条件：在家/夜间。

8. 实时事件

事件载荷用途
scene.run.started{ runId, sceneId, trigger }前端进入执行态
scene.run.updated{ runId, status, actions[] }逐项进度
scene.run.finished{ runId, status, summary }完成/失败提示

9. 边界与防护

  • 循环触发：场景动作改变设备状态又触发同一场景 → 事件链去重/深度限制。
  • 并发执行：同一场景默认串行/拒绝；可配置排队。
  • 冷却时间：手动/条件触发加 cooldownSec，防抖。
  • 错过定时：服务重启后补跑策略（跳过/补一次）可配置。
  • 时区：家庭时区，cron 按本地时间；DST 明确策略。
  • 失败重试：只重试幂等命令；非幂等动作要谨慎。
  • 权限：执行前校验操作者属于家庭；系统触发用 system actor。

10. 扩展方式

新增触发器/动作：

  1. 在 strategy/trigger 或 strategy/action 注册处理器。
  2. 补 config schema 与前端配置表单（后台动态表单）。
  3. 补契约与执行器测试；不改核心状态机。

11. 验收

  • 手动执行场景，逐动作状态可见
  • 定时触发按家庭时区执行
  • 条件触发有防抖/持续判断
  • 部分失败标记 partial，原因可查
  • 重复执行被冷却/幂等拦截
  • 循环触发有深度限制
  • WS 断线重连后能拉取执行结果
