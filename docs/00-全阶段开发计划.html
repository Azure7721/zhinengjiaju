全阶段开发计划

把产品、架构、设备、账号、前后台和测试拆成 6 个可验收阶段。每个阶段都有明确的目标、 交付物、验收标准和下一阶段入口。本文档是总纲，细节落在 01–09 与 P0–P5。

6 个阶段 29–39 人日 T0 必做 T1 硬件加分

1. 项目目标

做一套可扩展的全屋智能小程序系统，而不是把设计稿上的几个按钮做出来：

  • 用户端：微信小程序，完成登录、家庭、设备控制、场景、配网、能耗、消息、我的。
  • 管理端：PC Web 后台，管理用户/家庭、设备型号/能力、设备库存、场景模板、日志与审计。
  • 服务端：账号、家庭、设备、场景、遥测、命令、权限、审计的 API 与实时推送。
  • 设备引擎：模拟设备信号；支持单机全虚拟与 ESP32 BLE 两种测试路径。
  • 扩展能力：新增设备类型/能力/场景动作尽量通过配置与注册完成，不改页面结构。

2. 范围与非目标

本阶段要做

  • 微信小程序用户端 + PC 管理后台
  • 微信登录（含 mock 模式）与管理员 JWT/RBAC
  • 家庭、成员、房间、设备绑定
  • 设备型号/能力元数据与动态 UI
  • MQTT/WebSocket 信号链路与模拟引擎
  • 场景触发器/动作/执行日志
  • T0 单机全虚拟 + T1 ESP32 BLE 测试
  • 部署、演示、验收文档

本阶段不做

  • 真实量产硬件与厂商云对接
  • 支付、订单、物流、发票
  • 语音助手、地图、复杂 AI 推荐
  • 多租户 SaaS 与大规模集群
  • 微信审核上线（只到体验版）
  • 商城/发现的重业务逻辑
  • 真实 BLE 之外的 Zigbee/Matter 网关

2.1 UI 空缺入口处理规则（设计稿有按钮、无对应页面）

设计稿只画了核心链路，很多入口“有按钮没有页面”。全部按以下两类处理，不允许静默点击无反应，也不允许因此膨胀范围：

类别判定标准处理方式范围约束
A · 必要 / 设置类 核心链路或账号/家庭/设备管理必需，缺了流程走不通或无法演示闭环 按现有 UI 风格新设计一个页面：沿用设计令牌（主色 #12BFC1、卡片、圆角、分组列表），只保留必要功能 不做全功能；每个新页面只覆盖验收所需最小操作集
B · 丰富但无 UI 的运营版块 内容运营类、重业务、设计稿无页面，如商城、发现、健康生活、会员中心 点击提示“正在开发中”：统一占位组件（Toast 或占位页），入口保留、可点击、有反馈 不做内容、不做后端接口；仅占位交互
  • A 类示例：设置（账号安全/通知/关于/通用）、家庭管理、房间管理、设备编辑（改名/移房间/删除）、WiFi 与网络、退出登录、消息通知详情。
  • B 类示例：发现、商城、健康生活、会员卡/权益、耗材商城、第三方平台。
  • 分类清单在 05 · 小程序用户端 的“入口盘点”表中逐条给出；开发中若发现新入口，按本规则归类并回填该表。
  • 两类都计入 P3 验收：A 类可走通、B 类点击必有“正在开发中”反馈。

3. 架构原则（必须可验收）

原则落地方式验收信号
元数据驱动设备型号、能力、命令 schema 存库；小程序/后台按元数据渲染后台新增设备型号，小程序无需改代码即可控制
能力注册表capability → 控件映射；未知能力有通用降级新增 capability 不复制页面
协议适配器Mock / VirtualBle / MQTT / RealBle 统一接口切换传输不影响业务层
命令总线校验、幂等、超时、重试、ack、审计重复 cmdId 不重复执行
场景 DSL触发器/条件/动作策略注册；执行器状态机新增触发器类型只加策略
动态 UI小程序控制区、后台表单由 schema 生成设计稿 4 类设备只是首批模板
权限与版本RBAC、API 版本化、审计日志越权请求被拒绝且有审计
数据绑定设备添加落库并绑定 user/family/home后台可查、可解绑、可迁移

6. 跨阶段关注点

安全

JWT/refresh、密码哈希、RBAC、输入校验、限流、CORS、审计；设备命令校验归属，防止越权控制他人设备。

数据

PostgreSQL + Prisma；设备状态/遥测/命令/场景执行/审计留痕；JSONB 存能力与参数；索引与保留策略。

可观测

结构化日志、请求 ID、健康检查、关键指标（在线设备、命令成功率、场景失败率）；管理后台可见。

可复现

一键启动、种子数据、环境变量样例、Docker/本机降级、测试账号、重置脚本。

文档

每阶段更新 README、OpenAPI、数据字典、变更记录；计划文档与实现同步，不写“过期文档”。

可扩展

新增设备类型/能力/触发器/动作不复制页面；用元数据、注册表、策略与适配器扩展。

7. Definition of Done

  • 代码通过 lint、类型检查、单元/集成测试
  • 关键流程有 E2E 或可复现的手工验收脚本
  • API 有 OpenAPI 文档，错误码统一
  • 数据库迁移可重复执行，种子数据可重置
  • 设备添加落库并绑定账号，后台可查
  • T0 单机全链路通过；T1 至少扫描/连接/读取/配网/遥测
  • 小程序无控制台报错，关键操作有反馈
  • 管理后台权限菜单/按钮生效，写操作有审计
  • README 可让新人从零启动
  • 演示脚本 5–10 分钟可一次走通

8. 主要风险

风险影响应对
范围膨胀工期失控阶段验收以核心闭环为准；商城/发现只做静态
架构过度设计开发变慢先做最小链路，再按阶段补扩展点
Docker/WSL 不可用环境阻塞P0 三级降级：Docker → 本机服务 → SQLite/Aedes
没有 ESP32/蓝牙T1 无法做T0 单机全虚拟是必做基线，T1 加分
微信 AppID/域名真机/体验版受阻mock 登录 + 开发者工具 + 内网穿透
文档与实现脱节后续维护困难每阶段更新 OpenAPI/数据字典/README

9. 假设

  • 单人 + AI 辅助、全职投入估算；实际以验收为准。
  • 管理后台默认 PC Web；小程序内可保留可选的管理员入口。
  • 设备信号默认 MQTT + WebSocket；T0 全虚拟，T1 ESP32 BLE。
  • 数据库默认 PostgreSQL；SQLite 仅作环境兜底。
  • 本阶段只写计划文档，不写业务代码。
